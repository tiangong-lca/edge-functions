# edge-functions Validation Guide

## Default Baseline

Unless the change is doc-only, the default local baseline is:

```bash
pnpm lint
pnpm check
```

`pnpm check` first requires exact Deno `2.1.4` / bundled TypeScript `5.6.2`, Supabase CLI `2.121.0`, Node `24.19.0`, and pnpm `11.24.0`. It then checks every enabled `supabase/functions/*/index.ts` and `test/*.ts` root in one bounded shared graph, runs the Node contract tests, and executes the default Deno behavior tests while the credentialed live Upstash test remains ignored unless explicitly selected. The command reports actual inventory and test counts. Deno is the authoritative compiler; no npm TypeScript package participates.

Review note, 2026-08-31: Edge #357 upgrades every direct runtime/import dependency to the latest stable version verified for exact Deno 2.1.4, including OpenAI 7.8 and Supabase JSR 2.112.4. Validation requires empty `pnpm outdated` and exact-Deno `deno outdated --latest`, one import-map/direct-import contract, targeted OpenAI/Redis/Supabase/Auth checks, Redis 0.41.2's dual-provider signature adaptation, the canonical full gate, and no Portal credential/config mutation. Official OpenAI documentation continues to define `client.responses.create` as the primary JavaScript API; Chat fallback remains covered.

Review note, 2026-08-31: Edge #361 closes the Functions JS pin gap found during Production promote review. The dependency contract must scan every TypeScript source/test/script quoted specifier containing `@supabase/functions-js`, detect synthetic JSR, versioned JSR, npm, and HTTPS bypasses, accept only `@supabase/functions-js/edge-runtime.d.ts`, and resolve that alias to exact 2.112.4 in `supabase/functions/deno.json`. The rewrite is type-only; request examples and runtime behavior remain unchanged, and Portal Functions are not remotely deployed by this fix.

The current baseline intentionally skips:

- `antchain_*`

If you reactivate or rely on that route family, update the inventory and validation story in the same change. The retired generic non-FT embedding route is intentionally absent, while active `embedding_ft` routes stay covered.

The original five-package runtime group selects AWS SDK 3.1152.0, Redis 0.42.0, Supabase JS/Functions JS 2.118.0 and OpenAI 7.38.0; the explicitly approved scope extension also pins Zod 4.6.7. Preserve the exact supported Deno/TypeScript, auxiliary Node/pnpm, Actions and unrelated package inputs. CLI/Edge Runtime and formatter changes are separately owned by #496 and normally composed with #495 in this candidate. A runtime-only result does not establish a globally empty outdated inventory; audit both scopes together under the unchanged empty-inventory requirement.

`supabase_sdk_wire_test.ts` uses shared factories and real client transports to verify schema and credential headers, RPC/Functions serialization and errors, signed RS256/JWKS verification, cache reuse, invalid issuer/audience/signature rejection and explicit fresh-user identity checks. ### Browser preflight regression

For shared CORS changes, exercise actual cross-origin requests in both Firefox and Chromium with the complete Functions JS header set: Authorization, apikey, Content-Type, x-client-info, and x-region when a function region is selected. Isolated Firefox 140.0.2 and 153.0 regressions showed that wildcard header permission allowed POST but did not reuse its preflight cache; explicitly naming the SDK headers restored reuse. Keeping `*` alongside those names preserves other callers' header permission. Compare the old and new header policy across more than the browser's default cache lifetime, and prove that a changed/expired bearer still reaches authentication and receives 401 rather than reusing success. Include an additional caller header to verify wildcard compatibility. `test/command_runtime_test.ts` separately proves explicit SDK header coverage, preflight bypassing actor/business work, POST resolving its actor on every call, and unsupported methods remaining rejected. No response-cache directive or credential wildcard is introduced.

## Dependency proposals and scoped CI

The existing `CI` workflow runs on PRs to `dev` and `main` only when dependency manifests, toolchain selectors, Actions workflows, monitoring configuration/control tests or selected synthetic stack qualification inputs change. Stack inputs are the driver, its helper directory and Node test family, copied fixture/source manifests and the two actual imported Portal HMAC/transport helpers. Each such input receives the same single canonical job; unrelated runtime/test/docs paths stay outside this filter. Manual dispatch remains available. It checks out the exact PR head without persisted credentials and runs the same frozen install, `pnpm lint` and `pnpm check` commands. PR-number concurrency cancels superseded runs. Unrelated runtime or documentation PRs gain no extra automatic gate. There are no repository secrets, write permissions, privileged PR events, remote probes or deployments in this workflow. Same-repository origin is not trust; the gate grants no additional authority to bot or human authors. If intake or adoption logic needs bot identity, use the PR author, not the current event actor.

Dependabot version proposals target `dev`: root npm developer tools on Tuesdays at 05:00, Deno imports at 05:20, and Actions at 05:40, all Asia/Shanghai. Seven-day version cooldowns, two npm/Deno PR slots and one Actions slot bound traffic. Minor/patch updates are grouped by ecosystem; majors remain individual proposals. No automatic merge or dependency upgrade is authorized by monitoring.

The Deno entry selects `/supabase/functions`, whose `deno.json` owns the imports. Root `deno.json` only extends that file; the upstream updater fetches the selected manifest and declared workspace members, not `extends`, so a second root entry would not discover another graph. The canonical checks still validate the root configuration and all enabled source/test consumers. The upstream parser recognizes ordinary npm/JSR specifiers but does not match the retained `npm:/zod@4.6.7` spelling or either HTTPS mapping: `https://esm.sh/@upstash/redis@1.38.3` and `https://deno.land/x/postgresjs@v3.4.8/mod.js`. These three pins remain under explicit reviewed maintenance. Audit them and direct imports when their owner proposes an upgrade; do not relabel them as monitored registry dependencies or rewrite imports to make a scan look complete. Platform's generated Function mirror remains owned by its exact-Edge-commit refresh procedure; this rollout does not edit that mirror.

Keep exact Deno/TypeScript, Node/pnpm, Supabase CLI/runtime, Functions JS and other reviewed dependency contracts. New version proposals must pass existing pin and behavior tests; an intentional supported upgrade updates its owning contract and proof together. Actions monitoring does not update `with.version` scalar toolchain pins or raw runtime selectors; those remain explicitly reviewed tooling maintenance. GitHub currently documents pnpm through version 10, so a successful hosted npm updater and frozen pnpm 11 candidate install must establish actual lockfile compatibility rather than assuming it from configuration parsing.

Configuration activates only after it reaches default `main`; a merged `dev` PR does not activate discovery or establish root-main eligibility. Security proposals still target default `main` and use the controlled main-hotfix/backmerge route. The `target-branch: dev` options apply to version updates, so their groups, cooldowns and fixture exclusions do not configure default-main security behavior. Version exclusions use repository-relative paths without a leading slash. Verify repository alert/security-update settings separately; this file does not enable them or establish successful hosted scans. Discovery may proceed independently of adoption, but bot association/adoption remains blocked wherever the independent merge service's running author protection has not been verified. Never enable merging as a prerequisite for discovery.

The reviewed pnpm setup Action is v3.1.1 at exact commit `a0881977cd8ea73b1ed212236c99ca10dcc80cf4`. Its [tagged Action contract](https://github.com/pnpm/setup/blob/a0881977cd8ea73b1ed212236c99ca10dcc80cf4/action.yml) runs under Node 24 and supports the existing exact pnpm `version`, explicit `runtime`, `cache: true` and `install: false` inputs. The [tagged implementation](https://github.com/pnpm/setup/blob/a0881977cd8ea73b1ed212236c99ca10dcc80cf4/src/index.ts) honors the disabled automatic install, so the separate frozen installation remains the graph gate. Its runtime selector preserves auxiliary Node 24.19.0; it does not select or upgrade the authoritative Deno/TypeScript runtime. Keep the exact-action assertion and all canonical checks when qualifying a later proposal. Local source checks do not prove hosted Action execution or cache cleanup; retain the actual candidate CI logs separately.

Validation includes `node --test scripts/dependency-ci-contract.test.cjs`, frozen install, `pnpm lint`, `pnpm check`, and strict Docpact validation/lint. Preserve actual updater and candidate CI receipts before claiming hosted coverage. Source delivery, promotion, root integration and any later Function deployment remain separate outcomes.
